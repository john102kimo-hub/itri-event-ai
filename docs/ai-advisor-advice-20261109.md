## 四、兩個需要講清楚的地方

### 1. RAG 跟「坑 7 不用向量庫」其實不衝突

坑 7 反對的是**向量資料庫**（外部服務＋索引會過期），不是檢索本身。RAG 的本質是「先找對資料，再交給模型」。你現在的弱點不在單場內檢索（KB 小到整份塞得下），而在**選場與選意圖**：路由只看到每場的「名稱／日期／類型／有無資料」（`lib/router.js` 的 calendar cards），看不到內容。

所以建議的「RAG」版本是：**在每場的卡片上加一行摘要＋關鍵字**（幾十個字，由 KB 產生或同仁填），讓路由比對「這題在講什麼」而不只是活動名稱。這是檢索，零外部依賴，不違反坑 7。

### 2. 「問 A 答 B」與「胡言亂語」是兩種病

| 症狀 | 屬於 | 對應手段 |
|---|---|---|
| 問 A 場，回 B 場的內容 | 路由／綁定 | 記錄路由決策；卡片加摘要；群組綁定檢查 |
| 問產業趨勢，回活動議程 | 路由（意圖） | 同上；續問提示的判準 |
| 答案裡有資料沒有的數字、網址 | 出口檢查 | `ANSWER_GROUNDING` 從 shadow 改 `on:urls,terms`（先量誤報率） |
| 資料沒寫，模型自己補 | KB 缺口 | 母資料庫＋「這部分我沒有資料」的降級路徑 |
| 讀對資料但讀錯意思 | 模型理解 | 看 log 確認後再調 prompt 或換成更強模型，不要先猜 |

## 五、具體做法（照順序）

### 步驟 0：把每次回答的決策記下來（最優先，約半天）

在 `qa_log` 的 **J 欄之後**新增欄位（不動 A–I，後台分析與匯出讀的是 `A:I`，要先確認新欄位不會被 `readRange('qa_log!A2:I')` 以外的地方誤讀）：

- `intent`、`routed_event_ids`、`confidence`（路由結果）
- `context_source`：`1:1` 或 `group`；是用綁定、用自己上一題、還是路由選的
- `kb_source`：`knowledge_base`／`invite_letter`／`global`（母資料庫上線後）／`news`
- `grounding_flags`：`answer-grounding` 抓到的數字／網址／名詞（影子模式本來就算得出來）

兩個寫入點：LINE 在 `lib/line-reporter.js:1692`，網頁在 `api/chat.js:232`。寫入失敗不能擋回覆（現有 try/catch 已是這個寫法）。

### 步驟 1：收壞案例、分類、變成測試（1–2 天）

1. 從 LINE 截圖或後台 CSV 收 **5–10 則真實的壞回答**（群組與 1:1 都要有）。
2. 每則標一個階段：
   - (a) 群組觸發不該回卻回了／該回卻沒回
   - (b) 路由選錯場或選錯意圖
   - (c) 選對場，但 KB 沒寫
   - (d) KB 有寫，模型讀錯或亂補
3. 變成回歸測試：路由類放 `test/test-router.mjs`，對話類放 `tools/line-persona-sim/`。之後每次改動跑 `node test/run-all.mjs`。
4. 帶這份清單去問老師，比問「怎麼設計」有效得多。

### 步驟 2：依分類修（看步驟 1 的結果決定比重）

- **(b) 多 → 路由卡片加摘要與關鍵字**：`buildAllCalendarCards()` 回傳多一個 `summary`；後台新增活動時自動由 KB 產生、同仁可改。
- **(a) 多 → 群組行為檢查**：確認同一群組多人問不同場時，`getStoredEventId(groupId)`（群組共用一份綁定）與 `getGroupSpeakerEventId()` 的交互；確認 `recentTopicContext(groupId)` 在群組是以群組還是以個人為單位。**這兩點是推測的成因，要用步驟 0 的 log 驗證，不要先改。**
- **(c) 多 → 做母資料庫**（下一步）。
- **(d)／胡說 → 開出口檢查**：先用 `tools/grounding-backtest/` 丟真實問答回測誤報率，再把 `ANSWER_GROUNDING` 設成 `on:urls,terms`；數字類等回測過再加。

### 步驟 3：母資料庫 v1（步驟 1 確認 (c) 是主因才做）

**放什麼**（只放「工研院已公開、跨場次不變」的事實）：

1. 機構簡介與各研究所對應領域（`contacts-directory` 已有一半）
2. 非活動專屬的常見問答（怎麼申請採訪、授權洽談窗口、參訪怎麼申請）
3. 名稱對照：正式中文名／縮寫／英文名（也能順便降低 `answer-grounding` 的英文名詞誤報）

**不放什麼**：
- 「不可跨場歸納、不報價」這類規則——已經在 `lib/prompt.js` 與 `lib/audience.js` 的出口，維持在程式裡。
- 任何會變動的數字（今年發表幾項、營收）——放進去就會過期，又變成「替主辦單位發言」（坑 6）。

**怎麼存**：沿用 `contacts-directory` 的做法——Sheets 新分頁，後台一個 textarea 編輯，格式一行一條，不用另外做表單 UI。

**怎麼用**：不是每次全塞。路由新增一個意圖（暫名 `org_faq`），或在 `qa` 且該場 KB「這部分我沒有資料」時才載入。優先順序：**該場 KB／新聞稿 > 母資料庫**；兩邊說法不同時並列並標出處（跟坑 6 的「不自行挑一個」同一個原則）。大小控制在 8000 字以內。

**回答梯度**（把現在零散的降級串成明文流程）：
該場 KB → 母資料庫 → 官網新聞補查（現有 `NO_DATA` 路徑）→ 轉新聞聯絡人。每一層都要在 `kb_source` 記下來。

### 步驟 4：之後才考慮

- 單場 KB 超過 45000 字、或場次到上千場，才評估真正的向量檢索。
- 群組裡用 LINE 按鈕或「@米亞」才觸發，降低誤觸（看步驟 0 的數據再決定）。

## 六、不建議做的事

- **蓋一個大型向量資料庫**：規模用不到，且違反坑 7。
- **把所有場次的知識庫合併成一份大 prompt**：這正是老師說的「全部傳給 AI 讓它自己判斷」，會更容易問 A 答 B。
- **把「不要亂說」寫進母資料庫當規則**：出口擋得住的才算數，見 `CLAUDE.md` 第 2 條。
- **在沒有壞案例前就改 prompt**：現在不知道壞在哪一關，改了也無法驗證。

## 七、驗收（你自己能做的）

1. 步驟 0 完成後，隨便問 5 題，後台匯出的 CSV 看得到每題的 intent、選到哪一場、用哪份資料。
2. 拿步驟 1 的 5–10 則壞案例重問一遍，哪些還壞、壞在哪一階段，一目了然。
3. 母資料庫上線後，問一題「某活動 KB 沒寫、但機構層級有答案」的題目（例如「採訪要找誰」），答案來自母資料庫、且標示出處；問一題兩邊都沒有的，要老實說沒有資料。
4. 問一題兩邊矛盾的，要並列而不是擇一。
