### 批次 57：全面盤點「記者問得到嗎、會不會出 bug」（盤點，2026-09-12）

這一批不是回報，是使用者要求**整個盤一次**：「使用者透過 LINE 問問題的時候，他可不可以
回答解答他所有的問題，以及不會出現所謂的 bug」。

前 56 批都是「有人回報 → 修那一個」。這次反過來做：把記者實際會打的句子整批餵進判斷
規則、把 Sheets 換成會壞掉的版本跑一遍、把每一個對外呼叫的逾時清單列出來。掃出四件事，
其中兩件是我們自己的規則造成的答非所問，兩件是**只要正式站稍微不順就會發生、而且完全
沒有徵兆**的沉默。

#### 一、例外 ＝ 記者面對已讀不回（最嚴重）

`api/line.js` 的 `handler` 對每一則事件包了 try：

```js
try { await handleEvent(ev); }
catch (e) { console.error('LINE 事件處理失敗:', e.message, ev?.type); }
```

這段是對的（不能回 500，LINE 會重送整批），但它**只跟我們自己講話**。實測把 `events`
表的讀取換成會丟例外的版本：

```
LINE 事件處理失敗: Quota exceeded for quota metric read requests message
【A】events 表讀不到時，記者收到的訊息數 = 0
```

零。記者送出問題，畫面上什麼都沒有，HTTP 照樣 200，Vercel Logs 很乾淨。

**這不是理論上的邊界情況。** `lib/sheets.js` 自己的註解就寫著：配額是每個服務帳號每分鐘
讀寫各 60 次、全站共用，「記者會當天幾十位記者在開場後十分鐘內集中發問，很容易瞬間撞到
配額」。也就是說，這個 bug 最會發生的時刻，剛好是最不能出事的時刻。

而且 `getAllEventRows()` → `readRange()` 沒有 try，它又是 1 對 1、群組每一條路都會經過的
那一張表（活動清單、換場判斷、按鈕辨識都要讀）——一張表出狀況，整個帳號靜音。

修法是在出口補一支 `apologise()`：例外之後回一句人話，並給下一步（洽新聞聯絡人）。
補在 handler 的 catch、不是在每一支可能丟例外的函式裡各自 try——這是**結構性保證**，
跟 `replyOrPush()` 包一層補群組導覽、`toTraditionalTW()` 擋在出口同一招（CLAUDE.md 第 2
條）。往後任何人新增一條問答路線、忘了接例外，記者一樣拿得到一句話。

⚠️ 群組的方向是相反的：**沒被叫到的訊息，就算出例外也不能開口**——那是插話，這個帳號
最該避免的事（第 8 節）。所以判斷只看事件本身（`mention` / 喚醒詞），不再碰任何會再丟
一次例外的 I/O。兩個方向都寫進測試，只測一邊會讓下一個人把它「修」壞。

#### 二、沒有任何一個對外呼叫有逾時

整條 LINE 路徑上的 `fetch()`——答題模型、意圖路由、工研院官網、IEK、Google Sheets——
一個 `signal` 都沒有。只有 `api/geo.js` 有（那支是 cron，反而不急）。

沒有逾時在 Vercel 上不是「慢一點」，是**整支 function 被砍掉**：`vercel.json` 給
`api/line.js` 的 `maxDuration` 是 60 秒，時間到 function 直接消失——沒有 catch 會跑到、
沒有回覆會送出。症狀跟上面第一項一模一樣（記者面對沉默），但成因完全不同，所以第一項
的修法救不到它：**根本沒有機會丟例外**。

逾時的價值不在省時間，在於**把沉默換成一句話**：`AbortSignal.timeout()` 觸發後 fetch 會
丟 AbortError，既有的 catch 就會回一句「目前無法取得回應」。

秒數沒有各自寫死，而是共用一個「這次請求的死線」（`REQUEST_BUDGET_MS = 55_000`，留 5 秒
給送出回覆與寫 `qa_log`）。理由是這條路會依序打好幾次外部呼叫（路由 → 答題 → 補查官網
最多 4 次 HTTP → 再一次模型），各自寫死的秒數看起來都很合理，**加起來卻會超過 60**。
死線是唯一算得準的東西：每一段都問 `msLeft()`，前面慢了後面自動讓路。

死線存在 `AsyncLocalStorage`（Node 內建，不破壞零依賴慣例）而不是模組層變數——同一個
執行個體可能同時處理兩個請求，共用變數會讓後到的把先到的死線往後推，先到的那個就會
以為自己還很寬裕，然後被砍掉，正好是這段要防的事。

#### 三、補查官網會把「已經算好的答案」一起拖下水

`answerQuestion()` 的順序是：拿到 AI 答案 → 判斷是不是「這場答不出來」→ 去官網補查 →
**兩段接起來才送出**。

補查那段最壞情況是：2 個候選關鍵詞 × 每個查無資料會去語助詞再試一次（見
`lib/itri-news.js`）＝ 4 次 HTTP，再加一次 Sonnet 把結果讀成答案。答題那段已經花掉的
時間再加上這一串，很容易撞到 60 秒——而被砍掉的那一刻，上面那句**已經算好的**、誠實的
「這部分我沒有資料」也跟著消失。

補查是加分（批次 31、37、38、39、44 一路加出來的），不能拿本來答得出來的東西去賭它。
改成吃剩餘預算：不夠就跳過補查，先把答案送出去；查到了但不夠再叫一次模型讀成答案，
就只附連結（那是批次 38 之前的行為，不是壞掉的狀態）。

CLAUDE.md 第 4 條「送出成功 ≠ 使用者看得到」再推廣一次：**算得出答案 ≠ 記者收得到**。

#### 四、「換個問題」會把記者踢回首頁

`SWITCH_RE` 的第一個分支是 `(換|切換|改)\s*(成|到)?\s*(一)?\s*(場|個|別場|其他場|其它場)`
——那個 `個` 沒有綁任何名詞。實測：

| 記者打的字 | 舊判斷 | 後果 |
|---|---|---|
| 換一個問題 | switch | `clearBinding()`，掃 QR 綁上的那場被清掉 |
| 我換個問題好了 | switch | 同上 |
| 可以換個說法嗎 | switch | 同上 |
| 換一個角度看 | switch | 同上 |
| 改一個問法 | switch | 同上 |
| 記者會換場地了嗎 | switch | 問這場會不會改地點，卻被踢回首頁 |

命中 switch 不是回一句話而已，是**真的解除綁定**（那是刻意的，見 `handleMetaIntent()`
的 switch 分支）。而「換個問題」正好是記者最自然的轉場語——等於他每講一次就被踢回
首頁一次，然後下一句話沒有場次可以回答。

修法：把「個」跟名詞綁在一起（換個**活動**／換個**場次**／換個**記者會**才算），並給
裸字「場」補否定前瞻（場地／場合／場面／場景／場所／場域／場館）。原本認得的講法
（換一場／換場／切換活動／回首頁／解除綁定…）一個都沒少，測試兩個方向都釘住。

#### 五、「這場還有哪些活動」回的是全站場次表

`CALENDAR_RE` 完全沒有錨定，於是任何一句「⋯有哪些活動⋯」都被當成「請列出全站有哪幾場
記者會」：

- 這場記者會還有哪些活動安排？
- 現場還有什麼活動可以參加？
- 這次記者會有哪些活動內容
- 請問展區還有哪些活動
- 會後還有其他活動嗎

這五句問的都是**這一場裡面**的事（議程、動線），拿到的卻是全站行事曆。這正是一路被
回報的那種答非所問，只是這次是我們自己的規則造成的。

判準：句子裡出現「這一場／這個現場」的指稱詞（這場、這次、本場、現場、會場、展區、
會後、當天…），或「活動」後面接的是議程類名詞（安排、流程、內容、議程…），那就是在問
這一場。時間詞（今天／明天／這個月）刻意不列——「明天有哪些活動」問的確實是行事曆。

**收緊會不會製造漏判？** 會，如果只做這一半。所以同一批補上第二層：

`handleEvent()` 與 `handleGroupMessage()` 綁定中原本只認 `industry_trend` 與 `tech_query`
兩種「跳出本場」的意圖，`routeIntent()` 判成 `calendar` 時**直接掉進 `answerQuestion()`**
——由那一場的 AI 拿它的知識庫回答「最近有哪些活動」。那正是 `handleMetaIntent()` 開頭
註解在講的原始 bug，只是換了一條路徑重演。以前沒被發現，是因為 `CALENDAR_RE` 幾乎什麼
都吃得下來，AI 那條路輪不到。

補上 `calendar` 分支之後，兩層各司其職：**規則保證按鈕與固定講法 100% 命中，AI 涵蓋
規則想不到的講法**（CLAUDE.md 第 2 條的分工）。三個呼叫端共用同一支 `sendCalendarReply()`
——記者不該從「怎麼問到的」看得出差別。

#### 這次的教訓

**「已讀不回」是這個帳號最貴的失敗，而它在 log 上完全看不出來。** 前 56 批修的幾乎都是
「回錯了」，因為回錯了看得見、會被截圖傳給朱朱。這次掃出來的第一、二、三項全部是「什麼
都沒回」——它們不會被回報，因為記者只會覺得「這東西怪怪的」然後改用電話。

所以盤點的方法不能只是重讀程式碼問「這樣對嗎」，要**主動把東西弄壞再看記者那邊剩下
什麼**（`test/test-resilience.mjs` 就是把這件事變成常態測試：把 Sheets 換成會丟例外的
版本，斷言記者收得到話，而且群組不會因此插話）。

第二個教訓：**規則寫太寬跟寫太窄，代價不對等，而 `lib/menu.js` 開頭那段原則寫的是
「寧可漏判也不要誤判」——第四、五項當初都寫反了。** 漏判會落到 `routeIntent()`，那是
一張還算可靠的網；誤判是直接把記者的問題換成別的東西（清掉綁定、丟全站清單），沒有
第二層接。收緊規則的前提是那張網真的在——所以第五項一定要連同 `calendar` 分支一起改，
只做一半反而更糟。

### 批次 58：追問不是只有「太空」那一種形狀（回報，2026-09-13）

回報的三張截圖，是一段連續的對話：

```
記者：工研院創新日          → 米亞：（創新日的活動摘要，軟綁定到這一場）
記者：媒體邀訪需求          → 米亞：（新聞聯絡人）
記者：產業趨勢分析          → 米亞：最新兩則是 9/7 的歐盟晶片法案 2.0…另一則人型機器人…
記者：有談機器人發展的嗎    → 米亞：有的，這場「智動新未來」相關議程佔了不少篇幅：
                                    13:30-13:35 引言｜國產機器人產業布局…
```

使用者的原話：「前面問產業趨勢 然後問機器人發展 但跳出不是相關趨勢 而是創新日這場活動」。

記者問的是**剛剛那則人型機器人的 IEK 摘要**，拿到的是**創新日的議程表**。答案本身沒有錯
（那場真的有機器人議程），錯的是他問的不是這件事。

#### 一、為什麼批次 24 的話題記憶沒接住

批次 24 修過一次幾乎一樣的病（記者問完趨勢打「太空」，收到「我沒抓到您想問哪一場活動」），
當時做了話題記憶：答完趨勢／技術題就把話題記進 `line_users` H 欄，下一則 `routeIntent()`
多拿到一個提示。這次那個機制**有生效、記憶也在**，還是錯了。

問題出在提示的寫法。批次 24 的版本是這樣講的：

> 這則訊息如果**只是一個產業或技術名詞**（例如「太空」「半導體」「光通訊」）、**或是
> 「那ＸＸ呢」這種省略式的追問**，那就是記者在接著同一個話題換個領域問…

它列的是**形狀**，而且只列了兩種。「有談機器人發展的嗎」是一句完整問句，兩種都不是，
於是這塊提示對它等於沒有意見。判斷權就落回上一塊提示——「目前這個對話正在問的是
《工研院創新日》這一場…看起來像是在延續、追問這場活動的內容，請判成 qa」。而
「有談機器人發展的嗎」讀起來**確實**很像在追問一場活動。

更糟的是，這兩塊提示對同一句話會給出**相反的答案**，而當時決勝負的方式只是「話題那塊
排在後面，是模型看到的最新一條指示」。那是位置上的暗示，不是講出來的規則——實測就是
輸給了前面那塊。

#### 二、兩件事都要修，而且不能只多列一種形狀

「再補一種形狀」是最直覺的修法，也是錯的。形狀列不完：

```
有談機器人發展的嗎 / 有沒有講到 AI 晶片 / 那篇在講什麼 / 還有別的嗎 / 連結給我
```

這跟 `looksLikeBareTopic()` 當初的教訓一樣（批次 27：擋得住「你好」，擋不住「天氣如何」，
而修法不是把「天氣」加進黑名單）。要找的是**判準**，不是清單。

**① 提示改講判準，並明寫否定清單。** 接續的定義是「他問的是不是我剛剛給他的那份資料」，
跟句子長什麼樣無關。反過來明確列出三種「才算真的跳開話題」：訊息裡有某一場的名稱或明確
線索、用了「這場／這次／本次／現場」這類指著某一場的說法、或明顯無關。給模型一份**收斂
的否定清單**，比給一份列不完的正面清單可靠。

**② 衝突規則寫出來，不要靠排序暗示。** 活動那塊提示現在會明講：「下一段講的是剛剛真的
發生過的事，比這段更貼近當下；兩段對同一句話給出不同答案時，一律以那段為準。」只在真的
有話題提示時才加這句（沒有話題記憶時憑空提到「下一段」會讓模型去找一段不存在的話）。

**③ 連「上一則實際答了什麼」一起帶給路由。** 這是真正把判斷從「猜」變成「查」的一層。
H 欄只記得住一個分類標籤（`industry_trend`），標籤給不出任何依據判斷「機器人」指的是剛剛
那則摘要。現在答完趨勢／技術題會把**答案節錄**一起記進 `line_users` I 欄，路由提示裡附上
那段節錄：「這則訊息提到的東西如果在下面出現過，那幾乎一定是在追問同一件事」。於是
「機器人」三個字剛剛就在自己的答案裡，不用猜。

⚠️ 借用 I 欄（`last_turn`，批次 28 的上一輪對話記憶）而不是再開一欄。趨勢題答完之後，
「上一輪」本來就是這一題。`e` 欄位填 `#topic:industry_trend` 這種前綴，永遠不會等於任何
真實的活動 id——`buildTurnHistory()` 比對的是「上一輪答的是不是同一場」，比不中就不回放，
所以這些列絕對不會被當成某一場活動的脈絡餵進問答（那正是批次 28 第三個 ⚠️ 在防的事）。

⚠️ 節錄只放**我們的答案**，不放記者上一則的問題。群組裡上一則的問題可能是別人打的
（批次 28 的同一個顧慮），我們自己的答案沒有這個問題，所以群組也能安全地用這一層。

#### 三、這件事為什麼留在 prompt，不是寫成規則

CLAUDE.md 第 2 條的判準是「這件事偶爾沒照做會不會出事」。意圖判斷本質上沒有一條死規則
分得開「有談機器人發展的嗎」是在問趨勢還是在問活動——**同一句話在不同的前一輪下，兩個
答案都對**。硬寫一條正則只會製造批次 27 那種「擋得住一句、誤傷十句」的黑名單。

所以這一批走的是另一半：**能寫成程式保證的，是把判斷需要的事實準備好**（③ 的答案節錄是
一次確定的讀寫，不是請求），prompt 只負責用那份事實做判斷。測試也照這條線切——
`test/test-router.mjs` 驗「該給的提示與節錄有沒有真的組進 system 區塊」，
`test/test-flow.mjs` 情境 19-2 驗「整條路走完之後，記者拿到的是趨勢還是那場議程」。

#### 四、反向的那一邊也要有測試

加寬涵蓋範圍最容易壞掉的是反面：話題記憶還在，但這句話**真的**在問目前這一場。情境 19-2
第三個 check 就是這個（綁定 quad、話題記憶是 industry_trend、打「這場的主要發表內容是
什麼？」→ 照樣交給 quad 回答）。那份否定清單就是為了這一邊存在的，只測一邊會讓下一個人
把它「修」壞——跟批次 57 群組那兩個相反方向同一個道理。

⚠️ 測試的假路由（`test/fakes.mjs`）刻意把話題追問排在**活動關鍵字比對之前**，並用 quad
那場當綁定——因為 quad 的關鍵字裡就有「機器人」，正是回報截圖的形狀：追問的詞跟某一場
活動真的撞名。排在後面就永遠輪不到，測不出這次要修的東西。

### 批次 59：排版很亂，而且五條路都一樣亂（回報，2026-09-13）

回報只有一句：「文字排版很亂 能夠精進嗎 整體上」，附兩張截圖。兩張是**不同的壞法**：

**截圖 ①（產業趨勢，問「有 ai 相關嗎」）** 把「9/6 人型機器人」與「8/6 CPO」兩篇報告
擠進同一段，手機上是十幾個視覺行的一大坨字，記者要自己在裡面找哪一句屬於哪一篇。

**截圖 ②（活動問答，問「演講者有誰」）** 其實**有**結構——開場暨引言／國際論壇／淨零
永續專題／永續能源專題／智動機器人專題，每組一行——但沒有項目符號、組跟組之間沒有空行，
一樣糊成一塊。

#### 一、三個根因，沒有一個是「模型不聽話」

**「N 行以內」在手機上不是一個有意義的單位。** 四條路線各自寫著 5 行／4 行／4 行／3 行，
而模型把「行」讀成「句」或「段」——截圖 ① 在它眼裡確實是「4 行以內」。手機一行只放得下
大約 16 個中文字，「行」這個詞在模型跟畫面之間根本對不起來。

**兩條既有規則互相打架。** `lineExtraRules()` 說「需要條列就用『・』開頭」，`TONE_RULE`
說「不要用一長串條列把記者淹沒」。模型同時收到「該條列」與「不要條列」，交出來的是最糟
的組合：**列了一長串、卻不用符號也不換行**——截圖 ② 正是這個形狀。這條是批次 28 為了
「人味」加的，本意沒錯（不要每句話都拆成一項），但寫成了否定「條列」這個技巧本身。

**沒有任何一條規則提過「空行」。** 手機可讀性最關鍵的一件事，四條路線一個字都沒寫。

#### 二、「整體上」是這次的重點

回報說的是「整體上」。排版不是某一條路的問題——活動問答、產業趨勢、工研院技術、官網
補查、智慧兜底五條路全都有。所以 `LAYOUT_RULE` 放在 `askAnthropic()` 的**共用 system
區塊**（跟 `ZH_TW_RULE` 同一個位置），不是各路線各寫一份：寫一次五條路一起受惠，以後
新增第六條也不會漏掉。

這正是批次 53「三個各說各話的字數上限」的教訓——同一件事散在好幾個地方各寫一份，遲早
漂開。`test/test-flow.mjs` 情境 24 就是那份「不准漂開」的保證：五條路各驗一次規則有沒有
真的到得了，任何一條被改成繞過 `askAnthropic()` 就會紅。順手把 `TONE_RULE` 裡那句打架
的話改掉（改成針對**數量**而不是否定條列這個技巧），並補一條測試釘住它不會被加回來。

規則本身講的是結構，不是長度：段落之間空一行、兩則以上一定條列、標題與說明分行縮排、
開場與收尾各自成段，並明講「其他規則裡的『幾行』指的是段落數，不是手機上的視覺行數」。

⚠️ **刻意不動既有的字數上限。** 回報講的是排版不是太長，改那幾個數字是另一件事，而且
改壞了會讓答案變得不完整。

#### 三、程式那一半只做零風險的事

`tidyLineLayout()` 補在 `stripMarkdownForLine()` 旁邊，同一個出口。它**只加空行、只刪
行尾空白**，永遠不切開、不搬動、不刪除任何一個字：條列區塊前後補空行、縮排續行要認得
出來（不然會在項目和它自己的說明中間插空行，比原本更亂）。

⚠️ **刻意不做、而且寫進註解免得下一個人順手補上**：把同一行裡的多個「・」拆成多行。
看起來是這支最該做的事，實際上會切壞人名——「・」是日文中黑點（U+30FB），中文譯名本來
就用它當分隔（「史蒂夫・賈伯斯」「馬丁・路德・金恩」），拆行就變成兩個人。而記者會直接
截圖引用這則回覆，把人名切成兩半的代價遠高於「條列擠在同一行」這個純粹難看的問題。
`test/test-layout.mjs` 第二節就是這個決定的守門。

順序也不是隨便排的：先 `stripMarkdownForLine()`（把 `- 項目` 換成「・」）、再
`tidyLineLayout()`（認的就是「・」開頭的行）、最後 `toTraditionalTW()`。

#### 四、為什麼主力留在 prompt

CLAUDE.md 第 2 條的判準是「偶爾沒照做會不會出事」。排版難看不會出事，而且「怎樣算排得
好」要看這一題有幾則資料、每則多長——沒有一條死規則做得到。這次跟批次 58 是同一種分工：
**能寫成程式保證的是零風險的機械修整，判斷本身留給 prompt。**

也因此有個誠實的但書：`test/test-layout.mjs` 測得出「出口有沒有把該補的空行補上」，
測不出「模型排得好不好看」。後者只能在 LINE 上實際問一輪。

### 批次 60：動畫早就做好了，只是掛錯地方（回報，2026-09-13）

回報：「有時候思考會很久 有可能固定出現像截圖這種… 讓大家知道其實有在思考」，截圖是
LINE 的「輸入中」動畫（那三個點）。

聽起來像是要做一個新功能，其實不是——**那個動畫早就做好了**（`lib/line.js
startLoading()`，打 LINE 的 `/chat/loading/start`）。關鍵字是回報裡的**「有時候」**。

#### 一、為什麼「有時候」

因為呼叫它的地方只有一個：`answerQuestion()`，也就是五條答題路線裡的「活動問答」。

於是記者的體感是這樣的：

| 問什麼 | 有沒有動畫 | 實際要等多久 |
| --- | --- | --- |
| 某一場活動的內容 | ✅ 有 | 只打一次模型，**最快** |
| 產業趨勢 | ❌ 沒有 | 先抓 IEK 網站 → 再打模型 |
| 工研院技術 | ❌ 沒有 | 先查官網搜尋 → 再打模型 |
| 最新新聞 | ❌ 沒有 | 先抓官網清單 → 再打模型 |
| 任何掉進智慧兜底的問題 | ❌ 沒有 | 路由 → 兜底模型 |

**會動的那條，恰好是最快的那條。** 真正會讓人等到懷疑「是不是壞了」的那幾條，畫面上
完全沒有反應。截圖裡動畫之所以出現，是因為那一題剛好被判成活動問答。

#### 二、改放在 1 對 1 的咽喉點，不是各路線各加一次

移到 `handleEvent()` 裡 1 對 1 分支的最前面——在路由、Sheets 讀取、模型呼叫**全部
之前**。三個理由：

1. **五條路一次到位**，以後新增第六條也不會漏掉。跟批次 59 的 `LAYOUT_RULE`、批次 57
   的 `apologise()` 是同一招：結構性保證，不是靠每個呼叫端記得（CLAUDE.md 第 2 條）
2. **慢的不只是模型。** `routeIntent()` 自己就有 15 秒逾時、Sheets 也可能卡在配額重試。
   放在答題函式裡的話，這段等待時間畫面上仍然是死的
3. **快路徑一起蓋到也沒有副作用。** 活動清單、使用說明一兩秒就回覆，動畫只會閃一下就
   被訊息蓋掉（LINE 收到訊息會自動收掉動畫）——而「固定會出現」正是這次回報要的

順帶把 `answerQuestion()` 的 `loading` 參數整個拿掉：群組走到那支時本來就不該有動畫，
移上去之後靠「這段在群組分流之後」這個結構自然成立，不必再靠呼叫端記得傳 `false`。

#### 三、要 await，而且要有逾時

**要 await。** 不 await 的話有機會「訊息先送到、loading 才送到」，變成答案底下掛著一個
沒人收得掉的動畫，整整轉 55 秒——比沒有動畫更糟。

**所以必須有逾時。** 這支從「只有活動問答會呼叫」變成「每一則 1 對 1 訊息都會呼叫」，
它現在擋在記者那一題的最前面。而 `lib/line.js` 是批次 57 補逾時時**唯一漏掉的檔案**
（router／industry-trends／itri-news／sheets／`askAnthropic()` 都補了）。LINE API 只要
「連上了但不回應」，記者等到的就不是慢一點的答案，而是整題卡死——批次 57 講的那種沉默，
換一個入口重演一次。給 3 秒：動畫是加分、答案是本體，3 秒不回就放棄往下走。

⚠️ 逾時**只加在這個加分型的呼叫上**，`callLineApi()` 的 `timeoutMs` 刻意不給預設值——
reply／push 那些真正在送訊息的呼叫維持原狀。訊息沒送出去等於記者已讀不回，跟一個動畫沒
跑出來完全不是同一個量級的代價，秒數要另外想清楚，不該夾在一個加動畫的修改裡順手改掉。
**`lib/line.js` 的送訊息路徑仍然沒有逾時，那是已知的缺口，留給下一批。**

#### 四、群組拿不到，而且刻意不補

LINE 的 `/chat/loading/start` 官方文件明講只支援一對一，group／room 傳了穩定失敗。
要讓群組有同樣的體感，只能改成先送一則「稍等一下」的訊息——那等於每一題都洗兩則版，
正是這個帳號最該避免的事（第 8 節）。**不做**，並在測試裡留一條反面守門。

#### 五、一條差點變成假性通過的測試

第一版把「智慧兜底」混在「每條路都要有動畫」那個迴圈裡，而那個迴圈前面設了活動綁定
——同一句話會被 `routeIntent()` 判成「延續目前這場」而掉進活動問答，也就是**本來就有
動畫的那條路**。還原程式碼做反向驗證時，那一條照樣綠。

一條永遠不會紅的測試比沒有測試更糟（批次 55 學過同一件事）。改成獨立一段、不設綁定，
並同時斷言「真的走到兜底那條路」（`kind === 'fallback'`），而不是只看動畫有沒有跑。

### 批次 61：綁定中點「新聞稿」→ 答成工研院整體最新新聞，不是這一場（回報，2026-09-15）

**回報的原話流程**：群組裡打「創新日」，米亞正確答出工研院創新日那一場的資料（時間
地點、主題、四大展區）。接著點了那一場的快速提問按鈕「新聞稿」，拿回來的卻是「工研院
官網新聞中心最近發布的新聞」清單（ICT TechDay、VAMAS 國際研討會…）——沒有一則跟創新日
有關。記者要的是**這一場**的新聞稿，拿到的是**全站**的新聞清單。

#### 根因：`routeIntent()` 的 systemPrompt 自己講出了會蓋過 currentEvent 提示的例子

`lib/router.js` 的 tech_query 說明裡有這一句（原本是為了接住「工研院最近發了哪些新聞／
新聞稿」這種完整句子）：

> 問「工研院最近發了哪些新聞／新聞稿」這種不指定技術領域的問題也算 "tech_query"
> （資料來源同樣是工研院官網新聞中心），這時候 tech_keyword 就留空字串

這條規則的本意沒錯，但同一份指示也讓模型看到孤零零的「新聞稿」三個字時往同一個方向
偏，蓋過了「目前綁定在這一場」那條 currentEvent 提示（該提示原本就講明：延續這場的
內容要判成 qa，只有明確提到「工研院」問整體技術，或明確問產業趨勢，才不要硬塞成 qa）。
「新聞稿」三個字本身沒有提到「工研院」，照 currentEvent 提示的規則應該留在 qa，但
tech_query 說明裡那句話舉了「新聞稿」當例子，兩條指示在模型眼裡打架，實測輸的是
currentEvent 那條。

這正是 CLAUDE.md 第 2 條的那句話——**「prompt 是請求，不是保證」**：模型九成九會照
currentEvent 提示判成 qa，剩下那一次就是這次記者截圖回報的那一次。而且這個帳號已經
特地為「新聞稿」這種泛用詞準備了正確的下游行為——`NO_DATA_GENERIC`／
`isGenericLookupKeyword()`（批次 44）：綁定中問「新聞稿」，這一場答不出來時要老實說
「還沒有完整新聞稿全文」＋給新聞聯絡人，**不是**被送去查全站新聞。問題出在請求
根本沒能走到那條已經寫好的正確路徑，卡在更前面的 `routeIntent()` 分類就被送去了
`answerTechQuery()` → 關鍵字是空的或泛用詞 → `answerLatestNews()`。

#### 修法：釘在程式出口，不是再去調 prompt 的用詞

同一個坑（規則講白了反而互相打架）已經在 `TOPIC_HINTS` 那段用「講清楚勝負」修過一次
（批次 58），這次不再往 systemPrompt 裡加字——那份 prompt 一長，類似的措辭衝突只會
越補越多，而且每加一句都要重新賭賭看模型這次聽誰的。

改成在 `api/line.js` 新增 `pinGenericTechQueryToEvent(routed, text, eventId)`：
`routeIntent()` 判成 `tech_query` 且抽不出 `tech_keyword`（代表模型自己也看不出具體
主題）、而訊息本身整字就是 `isGenericLookupKeyword()` 認得的泛用詞（新聞稿／照片／
資料／名單…，跟批次 44 那組判準完全同一份，不是另開一份新清單）時，直接把結果改判
回 `qa`、`event_ids` 釘住目前綁定的這一場，不再信任 `routeIntent()` 這次的分類。
兩個呼叫端（1 對 1 `handleEvent()`、群組 `handleGroupMessage()`）都套用同一支，理由
跟批次 59 的 `LAYOUT_RULE`、批次 53 的教訓一樣：同一件事只寫一份，不要兩邊各自維護
一份幾乎一樣的判斷。

⚠️ 只在 `tech_keyword` 是空字串時覆蓋：訊息若明確提到「工研院」或帶了具體主題
（「工研院院士授證的新聞稿」「半導體最近有什麼新聞」），`routeIntent()` 會抽出對應的
關鍵字，這種才是記者真的在問公司整體動態或另一個主題，不能覆蓋——覆蓋了反而會把
「這場真的沒有的話題」都硬答成這一場的內容，比原本的 bug 更糟。`handleUnbound()`
（完全沒有綁定時）不受影響：沒有場次可以釘，維持原本的判斷。

驗證：`npm test` 全部通過（既有的 22 條群組按鈕情境、批次 44 的泛用詞守門、批次 58
的話題續問測試都沒被動到，因為這些情境的假 Anthropic stub 本來就已經回傳正確答案，
這支只補的是**真實** Haiku 模型會誤判的那一次，測試環境本來就測不到）。

### 批次 62：天氣／告白這種閒聊，改成寫死的俏皮話（回報，2026-09-16）

**回報的原話**：附了兩張截圖——記者打「天氣如何」「我喜歡你」，米亞都用差不多的話說
「這題跟工研院活動或技術採訪沒關係，我幫不上忙」。回報問的是「有可能加入一些有趣
風趣回答，讓他更有生命力嗎，不適合會造成混淆就算了」——附了停損句，代表提問人自己
也在意「會不會反而搞砸」。

#### 為什麼不是直接放寬 `composeFallbackReply()` 的語氣

這兩句話現在都會落到批次 28 做的「智慧兜底」（`composeFallbackReply()`）：讓 Haiku
現場生成一句貼題的話。那支的 system prompt 把「不能提供事實內容、不能假裝查過」寫成
最硬的鐵規則，是這個帳號敢用 AI 兜底、掛著工研院名義還敢上線的前提。

如果做法是「在同一份 system prompt 裡多加一句『語氣可以風趣一點』」，等於在一份已經
靠嚴格措辭撐住安全底線的 prompt 裡，另外開一個「請自由發揮」的口子——跟 CLAUDE.md
第 2 節點名的四個坑（Markdown、`[[NO_DATA]]`、亂補新聞室資料、簡體字）是同一個形狀：
**模型抓對分寸的機率很高，但抓錯一次，就是官方帳號講了一句尷尬或失禮的話、被記者
截圖傳出去的那一次。** 風趣沒有客觀對錯可以拿來當輸出守門的判準（不像「有沒有
Markdown 符號」那樣能用程式檢查），一旦講砸了也沒有退回機制。

#### 改法：把「風趣」整個搬到程式碼裡，不留給模型

新增 `detectChitchat(text)`（`api/line.js`，`looksLikeBareTopic()` 之後）：只認得出
「天氣」「告白／搭訕」這兩類**不可能是真的在問工研院四條路任何一條**的閒聊，命中就
直接送出 `CHITCHAT_FIXED_REPLIES` 裡兩句我們自己寫、自己審過的俏皮話，**連 Haiku
都不呼叫**。風趣的部分完全鎖在這兩句寫死的文案裡，不會有「這次生成得比較尷尬」的
變數；認不出來的（絕大多數閒聊）維持原樣，照舊退回 `composeFallbackReply()`。

放在 `sendFallbackGuide()` 裡、`looksLikeBareTopic()` 之前——後者的裸主題詞判斷同樣
會誤收「天氣」兩個字，順序反過來的話「天氣」會先被複誦成主題詞。

⚠️ 判準刻意收得很窄：「喜歡」要接著「你」／「妳」才算告白（不誤傷「我很喜歡這個
研究題目」），「天氣」只收單獨出現、不收「溫度」（工研院真的有「溫度感測」這種技術
題）。跟 `looksLikeBareTopic()`／`SENTENCE_RE` 同一個原則——寧可漏判、退回智慧兜底，
也不要把真的提問攔截成一句風涼話。

驗證：`npm test` 全部通過，`test/test-flow.mjs` 新增情境 26，涵蓋兩件事——命中的兩句
閒聊改走寫死文案且不再呼叫模型（沒有 `kind:'fallback'` 節點），以及兩個容易誤判的
反例（「喜歡」沒接你／妳、「溫度感測技術」）照舊走智慧兜底不被攔截。

### 批次 63：主管實測回饋「有點太戲謔」，兩句改詞、加一句人設（2026-09-16）

**回報的原話流程**：批次 62 上線後，朱朱拿真的 LINE 帳號測給主管看。主管問「米亞你的
角色是公關小特派，問活動當天的天氣應該要知道」，米亞回批次 62 那句固定文案（「天氣
這題我真的槓龜 🌤️ …氣象台的活還是要問對棚的人」），主管的原話是「真的有點太戲謔
XD」。另外主管也問了「介紹一下你自己的個性」，這句沒有命中批次 62 收得很窄的兩類
（天氣／告白），落到智慧兜底，答出來的是「這題比較像是想認識我這個角色…我這邊沒有
這類設定資料可以查」——問個性、答成查無資料，比戲謔還尷尬。

#### 改法一：天氣／告白兩句拿掉俚語

「槓龜」是賭博／樂透用語，「問對棚的人」是演藝圈黑話——兩句都是台灣口語沒錯，但對
一個掛工研院名義、記者可能截圖引用的官方帳號來說，分寸比一般聊天帳號緊。改法不是
把「風趣」拿掉，是把「戲謔」換成「莊重」：拿掉賭博／演藝圈黑話，保留一點溫度（表情
符號、口語連接詞），但用字更接近正式場合會講的話。

```
天氣（舊）天氣這題我真的槓龜 🌤️ 我腦子裡裝的是記者會、產業趨勢跟工研院技術，
          氣象台的活還是要問對棚的人。要不要換個我答得出來的？
天氣（新）天氣預報不在我的守備範圍內 🌤️ 我專門處理記者會內容、產業趨勢跟工研院
          技術，這幾類的問題我很樂意幫忙，要不要換個方向問問看？

告白（舊）謝謝厚愛，不過我心裡只有記者會、產業趨勢跟工研院技術 😄 感情的事我
          幫不上忙，這幾題我可拿手多了。
告白（新）謝謝厚愛，不過我還是專心做好記者會、產業趨勢跟工研院技術這幾件事 😊
          這幾類的問題歡迎隨時問我。
```

「守備範圍」是棒球用語、「厚愛」是正式場合常見的客套話，兩個都不是俚語，但都還是
帶一點人味，不是公文腔。這份修改經過朱朱跟主管來回確認過才定案，不是自己單方面改。

#### 改法二：新增「問個性」一類，跟語音同一個道理

CLAUDE.md 第 3 節講得很清楚：米亞只有一種聲音，`tools/guide-video/voice/` 那顆語音
不用每次挑。個性介紹適用同一個道理——不該每次被問到都讓模型現場想一段不一樣的話，
應該跟語音一樣寫死一份、審過、固定下來。

`detectChitchat()` 新增第三類 `CHITCHAT_PERSONA_RE`，收「你的個性」「妳的個性」
「自我介紹」「介紹（一下）你／妳自己」這幾種問法：

```
我是米亞，工研院的公關小特派 🙂 個性算阿沙力——重點抓得到就直接講，不拖泥帶水。
專長是記者會內容、產業趨勢、工研院技術、媒體邀訪窗口，這幾件事問我最快，其他的
可能要請你問別人囉。
```

⚠️ 刻意不收「你是誰」「妳是誰」：`lib/menu.js` 的 `HELP_WHOAMI_RE`（整則訊息就是
「你是誰／你是什麼」這種問法）早就把這句接去 `detectMetaIntent()` 回使用說明，走在
`routeIntent()` 之前，這支根本輪不到。兩邊刻意分工：問「你是誰」是在問這個帳號是
什麼、該怎麼用，回使用說明是對的；問「你的個性」「介紹一下你自己」是在問米亞這個
角色本身，才是這次回報真正要接住的問題——如果 `CHITCHAT_PERSONA_RE` 也收「你是
誰」，兩條路對同一句話會給出不同答案，等於自己跟自己打架。

驗證：`npm test` 全部通過。`test/test-flow.mjs` 情境 26 補上第三類（問個性）與新的
反面測試——「你是誰」仍然走 `HELP_WHOAMI_RE` 回使用說明，不會被問個性那組寫死文案
接走。

#### 附帶討論：要不要真的接氣象 API，查活動當天天氣

主管問的原話是「問活動當天的天氣應該要知道」——這題目前判斷是**先不做**，原因記在
這裡免得下次又被重新問一次：氣象預報通常只有未來 7～10 天內準，記者會多半提早好幾
週就建好活動頁面，大部分時候問了也只會拿到「還沒有預報」；而且這會讓米亞的定位從
原本的四條路多長出一條氣象查詢，等於要多維護一支外部 API 串接跟一堆例外狀況（查不
到預報、活動地點寫得不夠精確等等）。如果真的是想解決「戶外活動要不要帶傘」這種實際
需求，比較划算的做法是同仁直接在那場活動的窗口分工或備註欄寫一句提醒，走現有的知識
庫機制就好，不需要另外接氣象服務。這不是不能做，是投入產出比現在還不划算，先記在
這裡，等真的有活動因為沒有這個功能吃虧了再重新評估。

### 批次 65：機構簡介＋三類新閒聊（2026-09-16）

**回報的原話**：「可否如果有人問介紹工研院等相關字眼，可否抓官網資料，並告知工研院
院長為張培仁、董事長為吳政忠，加上下列資料 [官網「工研院簡介」分類頁連結]」，接著
「另外，除了天氣告白問個性，也加入其他記者也可能問的場景」（原文「廠警」是「場景」
的同音輸入誤植）。

#### 一、「介紹工研院」要答對，不是被新聞稿清單接走

`介紹一下工研院` 原本沒對到任何規則，會掉進 `routeIntent()`：那支 `tech_query` 的
說明裡寫著「問『工研院最近發了哪些新聞／新聞稿』這種不指定技術領域的問題也算
`tech_query`，`tech_keyword` 留空」（`lib/router.js`），模型很容易把「介紹一下工研院」
也讀成同一類，送去 `answerTechQuery()` 查「最近新聞」——答非所問，記者要的是機構
簡介跟經營團隊，不是新聞稿清單。

驗證用官網連結前，先實際走過那個連結的導覽：`ListStyle.aspx?...MmmID=1036233406503070534`
是「關於我們 > 工研院簡介」分類頁，核心簡介文字是「工業技術研究院是國際級的應用
研究機構，以科技研發，帶動產業發展，創造經濟價值，增進社會福祉為任務」，頁面另外
連到「董事長」「院長」兩個子頁（各自的 `MmmID` 不同）。點進去核對：董事長子頁標題
是「吳政忠 董事長」，院長子頁標題是「張培仁 院長」——跟回報給的兩個名字一致。

跟院長／董事長姓名這種「錯了會很難看」的事實同一個道理（CLAUDE.md 第 2 節），這支
**不**靠模型現場答、也**不**即時解析官網頁面（HTML 結構隨時可能改版，解析壞掉又是
另一種「已讀不回」）：`lib/menu.js` 新增 `ORG_INTRO_RE`／`ORG_INTRO_TEXT`，直接寫死
一份審過的簡介 + 兩個人名 + 官網連結，接進 `detectMetaIntent()`（跟 `help`／
`org_intro` 前面那幾個 `*_EXACT_RE` 同一層，走在 `routeIntent()` 之前，不靠 AI 分類
猜對）。⚠️ **經營團隊異動時要記得手動更新這裡**——這不是會自動同步的資料，寧可資料
偶爾過時（記者還能點連結去官網核對最新資訊），也不要讓模型自己猜一個名字出來。

判準跟其他 `*_EXACT_RE` 一樣嚴格、整句錨定：只接「工研院是什麼／簡介／院長是誰」這
種問句本身就是在問機構整體的講法。「介紹一下工研院在半導體的技術」這種**後面還接著
具體主題**的問句不命中，繼續走 `tech_query` 查半導體——不能因為句子裡有「工研院」
兩個字就攔截掉所有帶主題的提問（測試有專門驗這個反面案例，見下方驗證）。

職員模式也借得到這條路（跟 `news`／`industry_trend`／`tech_query`／`contacts` 同一份
白名單，見 `handleStaffMessage()` 開頭「職員借用記者端意圖」那段），同仁一樣可能被
問「工研院是什麼」，不該落到職員自己的功能清單。

#### 二、新增稱讚、問是不是 AI、關心用語三類閒聊

跟批次 62／63／64 天氣、告白、問個性同一套架構（`detectChitchat()`／
`CHITCHAT_FIXED_REPLIES`）：句子本身不可能對到工研院四條路任何一條，才收進來，判準
一樣收得很窄。

```
稱讚（你好厲害、你好棒…）
謝謝誇獎，我會繼續加油 💪 不過真正厲害的是工研院這些技術跟記者會內容，我只是負責幫你講清楚——這幾類的問題我最樂意接。

問是不是 AI（你是AI嗎、你會不會被取代…）
是啊，我是 AI 沒錯 😄 不過我這個 AI 比較專一，只認真做記者會、產業趨勢跟工研院技術這幾件事，這幾類的問題我最拿手。

關心用語（辛苦了、你會累嗎…）
謝謝你這麼貼心 😊 我是 AI 不會累，隨時都能幫你查記者會、產業趨勢跟工研院技術這幾件事，有需要儘管找我。
```

「你是不是 AI」刻意不會跟 `lib/menu.js` 的 `HELP_WHOAMI_RE` 打架——那條錨定的是「你
是誰／你是什麼」這種問法，不含「AI」「機器人」這幾個字，兩邊不會對同一句話有不同
答案（跟批次 63 「問個性」刻意不收「你是誰」是同一個分工原則）。

同一批也把「問個性」那句的收尾再調一次：原本「其他的可能要麻煩你問別人囉」聽起來
像在打發人，改成「如果超出我理解的問題，請見諒QQ，或是可以聯絡我的同事們為您解答:)」，
先致歉再指路，語氣更軟。

驗證：`npm test` 全部通過。`test/test-flow.mjs` 情境 26 補上三類新閒聊，情境 27 新增
「介紹工研院」四種問法（含反面案例——後面接具體主題的問句不會被誤判）與職員模式
借用的驗證。
