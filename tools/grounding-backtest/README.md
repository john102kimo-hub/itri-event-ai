# 答案出口檢查回測工具

記者端的答案（網頁問答、LINE 問答）送出前，會檢查三件事：**答案裡的數字、網址、英文名詞，有沒有出現在模型當時看到的文字裡**（知識庫、活動基本資料、對話、記者的問題）。答案有、來源沒有，就是「新聞稿查不到」的疑點——模型編數字、編連結、編英文名稱，是最典型的幻覺，記者又會直接引用。

規則在 `lib/answer-grounding.js`（批次 132）。目前是**影子模式**：只在伺服器 log 記一行 `[grounding] …`，**不改任何一則回覆**。這支工具讓朱朱拿真實問答離線回測，看**誤報率**，再決定要不要把它打開；打開時可以先只提醒網址與英文名詞（`ANSWER_GROUNDING=on:urls,terms`），數字類留在影子模式（見第四節）。

只讀檔、不呼叫任何 API、不連 Google 試算表、不寫檔案；`npm test` 不會跑它。

## ⚠️ 先看這裡：真實問答含個資與未發布的稿件

回測要用的資料**不是公開資料**：

- 後台匯出的問答含**記者姓名、媒體名稱、提問原文**（個人資料）。
- 活動的 `knowledge_base` 可能是**還沒發布的新聞稿全文**（解禁前外流就是事故）。
- 回測**報告**會把每則被標出的答案的問題與答案前 80 字印在終端機——報告本身也含真實提問。

所以：

1. **不要 commit、不要上傳、不要貼到對話或工單。** 資料檔放在 repo 外面（例如桌面）最安全；一定要放在 repo 裡的話，檔名一律用 `*.local.json`（或 `*.real.json`）、CSV 用 `*.local.csv`，例如 `my-qa.local.json`、`qa-2026-10-12.local.csv`。`.gitignore` 已經擋掉這些檔名，以及後台匯出 CSV 的預設檔名（`all-events-qa-日期.csv`、`<活動ID>-qa-日期.csv`），避免 `git add -A` 一不小心就帶走。
2. **跑完就刪**：輸入檔、匯出的 CSV、`--json` 輸出存的檔，用完都刪掉。
3. **要分享報告給別人看，先遮掉提問原文**（或只貼各類別數字與 Top 項目那幾段，不貼「被標出的答案」那一段）。
4. `sample.json` 是**虛構**的範例（人名、電話、信箱都是假的），可以放心留在 repo 裡；用它練習時不會碰到任何真資料。

## 一、準備資料

輸入是一個 JSON 檔（範例見 `sample.json`）：

```json
{
  "events": [
    { "id": "活動 ID", "name": "活動名稱", "knowledge_base": "新聞稿全文",
      "event_date": "2026-10-28", "event_time": "09:00-12:00", "venue": "地點", "press_contact": "新聞聯絡人",
      "images": "https://example.org/p1.jpg|圖說一\nhttps://example.org/p2.jpg|圖說二" }
  ],
  "answers": [
    { "event_id": "活動 ID", "question": "記者問的問題", "answer": "AI 的回答",
      "asked_at": "2026-10-20T10:00:00+08:00", "expect": "ok" }
  ]
}
```

- `events`：把要回測的活動資料貼進來。`knowledge_base` 就是後台該活動的「新聞稿」欄位全文——**要跟當時 AI 看到的是同一份**。活動後來改過新聞稿，回測就不準。日期、時間、地點、聯絡人是後台同名欄位，沒填就留空字串。
  `images`（選填）是後台「圖片」欄的原文，每行「網址」或「網址|圖說」。線上模型看得到【本次活動照片】清單，回測也要帶，不然有人問過照片的答案（列出 3 個照片網址）會整批被當成編造連結；沒加 `--with-prompt` 時，回測會自己把這份清單補進去。
- `answers`：每則問答一筆，`event_id` 對到 `events` 裡的 `id`。找不到活動的會略過並在報告裡列出。
- `asked_at`（選填）：問的時間。活動基本資料裡有一行「現在時間」，沒給就用執行當下的時間；給了，那一行就跟當時一樣。
- `expect`（選填）：人工看過後標 `"ok"`（這則答案沒問題）或 `"flag"`（這則答案有問題）。報告最後會算出**誤報**（標了 ok 卻被標出）與**漏報**（標了 flag 卻沒被標出）。不標也能跑。
- 其他欄位（例如 `note`）會被忽略，可以隨手寫備註。

**直接用後台匯出的問答**：後台「匯出 CSV」下載的檔案（欄位：時間、活動ID、活動名稱、媒體名稱、姓名、記者問題、AI回答）可以直接餵給 `--answers-csv`，這時輸入 JSON 只要有 `events`，`answers` 可以是空陣列（CSV 的「時間」欄會自動當成問的時間 `asked_at`）：

```bash
# 檔名用 .local，並且放在 repo 外面或確定被 .gitignore 擋住（見上面的提醒）
node tools/grounding-backtest/backtest.mjs events.local.json --answers-csv qa-2026-10-12.local.csv
```

## 二、執行

```bash
# 先用範例跑一次，看報告長什麼樣子
node tools/grounding-backtest/backtest.mjs tools/grounding-backtest/sample.json

# 用自己的資料（真實資料，檔名用 .local.json；用完刪掉）
node tools/grounding-backtest/backtest.mjs my-qa.local.json

# 常用選項
#   --top 30          最常被標出的項目列前 30 名（預設 20）
#   --max-detail 50   只列前 50 則被標出的答案（預設全部）
#   --with-prompt     shownText 再加上整份 system prompt（更接近線上實際，標出數會略少；照片清單不管有沒有加這個選項都會算進去）
#   --json            輸出 JSON（給別的程式或試算表用）
```

## 三、怎麼看報告

| 區塊 | 看什麼 |
|---|---|
| 總則數、被標出則數與比例、每 100 則會多幾則提醒 | 被標出比例太高（例如三成以上）通常代表誤報多，先別打開。「只看網址＋英文名詞」另外算一行：那是 `on:urls,terms` 會提醒的則數 |
| 各類別 | 數字／網址／英文名詞各有幾則、幾筆。網址被標出幾乎都是真的問題（連結是編的）；數字最容易誤報（模型自己算的合計與換算） |
| 人工標註對照（有標 `expect` 才會印） | **誤報率＝標 ok 的答案裡被標出的比例**（也分數字／網址／英文名詞，並單獨算「只看網址＋英文名詞」）、漏報率＝標 flag 的答案裡沒被標出的比例。決定要不要打開，看的是這一段（見第四節） |
| 最常被標出的項目 Top 20 | 同一個項目一直出現，多半是規則該調的地方（例如某個產業縮寫、模型愛補的英文註解） |
| 被標出的答案 | 逐則列出問題、被標出的項目、答案前 80 字。**請人工逐則看：這個疑點是真的新聞稿沒有，還是無害的誤報** |

### 常見的誤報（看到這些就是誤報，不是真問題）

- **要外部常數的換算**：公尺/秒換成公里/小時（×3.6）、匯率（×32）、分秒換算。合計、平均、倍數、佔幾成、取整（新聞稿寫 1,234,567，答案寫「約 123 萬」）這類「兩個來源數字做一次加減乘除」的已經放過，不算誤報；但算式離得太遠（超過 150 字）、要外部常數、或數字前面沒有推算用語（共、合計、平均、增加、減少、佔…）的仍會標出——例如「較去年成長約 25%」（500 ÷ 400 − 1）、「年增 30 億元」。故意不把「成長、年增、提升」加進推算用語：編造的成長率正是長這個樣子。
- **沒有中文錨點的英文註解**：新聞稿沒有「物聯網」這個詞，答案寫「物聯網（IoT）」；縮寫的英文全名（`TFDA（Taiwan Food and Drug Administration）`）。新聞稿寫「邊緣運算」、答案補「（Edge Computing）」已經放過。
- **中英名稱對照表沒收的名字**：新聞稿寫「台積電」、答案寫 TSMC 已經放過（`NAME_ALIASES`，約 35 組）；沒收的名字（例如 NTUH）仍會標出。**回測真實問答後，把 Top 20 裡「其實是新聞稿中文名的英文寫法」補進這張表**，不要憑空擴充。
- **換寫法**：三成五↔35%、降低一半↔50%、上半年↔1 月至 6 月、1,000 瓦↔1 kW、電話改寫成 (03) 573-2100。頻率低，沒有為它們加規則。
- 其他：知識庫排版把網址切成兩段、人工在後台改過新聞稿但回測用的是新版。

### 仍會漏報的（沒被標出不代表沒問題）

- **整數 ≤ 10 的計數**（三位講者、五家廠商、公布了 7 項規格）：**刻意不查**。這類多半是模型照清單數出來的，來源不會逐字寫；品質審查補了一組「模型照清單數出來的 6～10 項計數」實測，把門檻從 10 降到 5 會讓其中 5／8 誤報，多抓到的編造計數只有 3／4——不是白賺。若要抓小計數編造，要用別的訊號（例如只在前面有「已有／已簽約／已導入」這類宣告用語時才查），不是單純降門檻。
- 其他小數字：新聞稿任何地方出現過同樣的小數字（日期、編號），答案裡同數值同類別就會過關。
- 張冠李戴：數字有出現在新聞稿裡，但說的是另一件事。
- **順著記者的問題說**：記者問「聽說投資超過 500 億元，對嗎？」，模型回「是的，500 億元」——問題也是模型看到的字，500 億元就「有出處」了。要擋得讓呼叫端把記者的話另外傳進來（`opts.userText`），目前沒做。
- **度量單位不分、幣別含糊**：28 奈米寫成 28 微米、1.5 瓦寫成 1.5 公斤都在同一類，抓不到；答案只寫「元」時對任何幣別都算（120 萬美元寫成 120 萬元）。
- **推算放行的代價**：前面有推算用語（共、合計、平均、增加、減少、佔…）的編造數字，碰巧湊得出來的會被放過；百分比最容易（見第五節）。
- **括號英文註解的代價**：括號左邊是新聞稿裡的具體名詞時（感測節點（Bosch）、晶片（Intel）），括號裡編造的英文名會被放過；「合作夥伴（Intel）」這類泛稱與清單（Intel、AMD）仍會標出。
- 人名、公司中文名、地名：不查。英文答案裡首字大寫的專有名詞（Intel、Samsung）也不查，只查縮寫、駝峰、帶數字的。
- 時刻（14:30）與換寫法（「下午兩點半」）：不查。
- 沒有 `http` 或 `www.` 開頭的網域（`itri.org.tw/news`）：不當成網址。

## 四、用誤報率決定要不要打開

`ANSWER_GROUNDING` 環境變數（Vercel）的寫法：

| 值 | 效果 |
|---|---|
| 不設、`shadow` | 影子模式（預設）：只記 `[grounding]` log，不改任何回覆 |
| `on:urls,terms` | **建議的第一步**：只有網址與英文名詞會進回覆後面那行提醒；數字照樣記 log、照樣出現在回測，但不提醒 |
| `on` | 三類（數字、網址、英文名詞）都提醒 |
| `on:numbers`、`on:urls`、`on:terms`、或用逗號接多個 | 只提醒挑的那幾類 |
| `off` | 完全關閉（連 log 都不記） |
| 其他任何值（打錯字、`on:url`、`on:urls;terms`） | 一律當影子模式，不會誤開 |

打開之後，被標出的答案後面會多一行提醒：

> ⚠️ 以上內容有幾處（2028 年、500 億元、80 家 等 6 處）在新聞稿原文裡查不到，引用前請向新聞聯絡人確認。

### 為什麼不能看「被標出的答案裡有幾成是真的」

以前這裡寫「被標出的答案裡，絕大多數（八成以上）是真的該提醒的，才改 `on`」。這個判準在真實流量上**不可靠**：它取決於編造的答案占多少，而真實流量裡編造一定很少。品質審查的資料有 28% 是編造的答案，所以那個比例看起來有 77.6%；真實流量只有 2%～5% 的答案真的編造時，以「五成忠實改寫、一成五照抄網址電話、兩成五對照、一成自己算或夾英文註解」的占比估算：

| 編造的答案占比 | 每 100 則答案會多幾則提醒（調整前 → 調整後） | 被提醒的答案裡真的有問題的比例（調整前 → 調整後） |
|---|---|---|
| 2% | 15.6 → 6.0 | 8% → 23% |
| 5% | 16.9 → 7.9 | 18% → 43% |
| 10% | 19.2 → 11.1 | 31% → 62% |

也就是說，**三類全開時，被提醒的答案裡多半仍是無害的**。所以改看兩個指標，報告的「人工標註對照」會直接算給你：

1. **誤報率**＝標 ok 的答案裡被標出的比例（`falseAlarm ÷ 標 ok 的總數`；報告也分數字／網址／英文名詞各算一次）。
2. **每 100 則答案會多幾則提醒**＝被標出則數 ÷ 總則數 × 100。

### 建議的做法（門檻可自己調整）

1. 把一段時間的真實問答（後台匯出）跑一遍，看**被標出的比例**與**每 100 則的提醒數**。
2. 抽出被標出的答案，逐則判斷是真問題還是誤報；順手在 JSON 裡標 `expect`（`ok` 或 `flag`），報告會算出誤報率。**標 ok 的答案要夠多**（至少幾十則），誤報率才有意義。
3. **先只看網址＋英文名詞**：誤報率 ≤ 3%、每 100 則提醒 ≤ 3 則，就改 `ANSWER_GROUNDING=on:urls,terms`。
4. **數字類另外看**：每 100 則提醒 ≤ 5 則，而且抽樣 20 則被標出的數字、人工看過八成以上真的有問題，才把 `numbers` 加進來（`on`）。數字類的雜訊主要是模型自己算的合計與換算，在真實流量的比例未知。
5. 如果多半是英文註解或模型自己算的數字，先別開，把 Top 20 項目帶回來調規則（白名單、單位、門檻、`NAME_ALIASES` 都集中在 `lib/answer-grounding.js`）。
6. 改成 `on` 之後，伺服器 log 的 `[grounding]` 還是會照記，可以持續對照。

## 五、規則調整之後的數字（批次 132 品質審查）

品質審查拿 10 場活動、322 則**自擬**的模型答案（照 Haiku／Sonnet 的慣用寫法虛構：條列、粗體、結尾警語、必要時中英並列）量過誤報與漏報。**這份資料不在 repo 裡**：聯絡資料雖然是編的，但寫得像真的（電話、`@itri.org.tw` 信箱），不適合留在 repo；要重跑請拿自己的真實問答，用上面的 `expect` 標註。

⚠️ 看這些數字要知道的三件事：

1. **資料是自己寫的，各類答案的比例也是自己定的**（忠實改寫 75、自己算 35、中英互譯 47、照抄網址電話 25、編造 72、對照 26、小整數 30）。分兩批：開發集 196 則是調規則時看的；第二輪開發集 114 則在大部分規則定案之後才寫，但有幾項調整看過它的結果才定案，所以**不算獨立驗證**。真正的誤報率只能靠真實問答回測。
2. **誤報率要看類別，不要看總表**。一般流量裡「模型自己算」與「中英互譯」的占比比這份資料低，以幾種不同占比換算，調整後的誤報率約 4.7%～11.7%（調整前約 15%～50%）。
3. 即使降到 7.6%，編造很少時被提醒的答案裡真的有問題的仍是少數（見第四節的表）。

另外兩組對照表（程式內沒有，是品質審查用的檢查）：101 組「不該標出」的忠實換寫，誤報 14 組 → 5 組；42 組「該標出」的錯誤寫法，漏掉 10 組 → 6 組。

### 推算放行的代價（碰巧湊得出來的編造數字會被放過）

對 10 場活動的知識庫，把「合計約 N 單位」的 N 從一個範圍掃過去，沒被標出的比例（推算前 → 後；推算前的比例是 N 本來就在新聞稿裡）：

| 計數（11～400 家） | 上萬人 | 百分比（2～99%） | 倍數 | 金額（億元） | 時間（年） |
|---|---|---|---|---|---|
| 1.7% → 6.4% | 1.1% → 7.9% | 10.5% → 22.2% | 14.1% → 18.3% | 0.1% → 0.5% | 24.9% → 26.2% |

百分比最多（可以拿來配的比例太多），所以**提醒裡的百分比要人工多看一眼**。另一個角度：把 160 則忠實答案裡的 635 個數字各改掉一點，調整後仍抓到 628 個（98.9%）。收得很窄的條件（只對直接比對失敗的數字、前面 14 字內要有推算用語、取整要寫「約」且同單位類別、時間類不做算術、運算元在新聞稿裡要相鄰、每則答案最多試 12 個數字）見 `lib/answer-grounding.js` 的 `derivableFrom()`。

### 沒有採用的建議，與理由

- **SMALL_COUNT_MAX 降到 5**：不採用，見上面「仍會漏報的」（正確的 6～10 項計數 5／8 誤報）。
- **電話格式統一成純數字**：不採用。提醒會顯示成「0800123456」；要做應該改成在掃描時抽一個電話 token，程式碼量比收益大。
- **度量單位分群（奈米／微米／公里）**：不採用。分群沒用，要換成同一個基本單位再比；頻率低。
- **英文答案裡首字大寫的專有名詞也查**（Intel、Samsung）：不採用。是擴大偵測而不是降低誤報，而且要靠停用詞表避開機構名的組成字（International、Center…），有過配風險；英文答案占比不高，等真實英文問答回測後再決定。
- **記者問題裡的數字不能替答案背書**：不採用。要同時改 `api/chat.js` 與 `lib/line-reporter.js` 的呼叫端，超出這次的範圍。
- **「小地方」裡的連字號後面的型號數字不另外標**：不採用。只影響提醒的項目數，不影響整則答案有沒有被標出。

## 六、log 長什麼樣子

影子模式與 `on` 模式都會在有東西被標出時記一行（只記被標出的項目本身，**不記答案全文、問題、使用者資料**）：

```
[grounding] where=web-chat event=e123 numbers=["2028 年","500 億元"] urls=[] terms=["Intel"]
```

`where` 是哪一條路（網頁或 LINE），`event` 是活動 ID（沒有就是 `-`）。在 Vercel 的 log 搜尋 `[grounding]` 就能看到線上實際的標出狀況，跟這支工具的回測互相對照。
